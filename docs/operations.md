# 运行、验收与恢复

## 日常观察

分别观察原生指标、可选 APIM 后端时延 p95 日志查询、告警状态、Logic App 运行、Named Value 内容和实际后端选择。它们不是同一时刻的强一致视图：

1. 请求完成后指标有上报延迟。
2. 规则按窗口评估后发出告警。
3. 控制器读取和条件写入名单。
4. 网关传播配置；已在途请求保留旧快照。

记录 UTC 时间、资源/模型、请求 ID、告警 ID、工作流 run ID 和 ETag 写入结果。不要记录完整 Authorization、APIM 订阅密钥、机器人 URL、SAS、用户提示词或模型响应正文作为默认诊断信息。

## 隔离环境验收

先准备维护窗口和恢复计划。不要用生产业务流量证明故障转移。

| 场景 | 预期 |
|---|---|
| 两个 Named Value 均为 `none` | 两组可正常调用，组内两端均有成功样本 |
| 仅一个成员降级 | 首次选择另一个成员 |
| 正常成员模拟 429/503 | 最多重试降级成员一次 |
| 全组降级 | 仍可转发，而非因零健康成员返回 503 |
| 401/403/404 | 不扩大重试范围 |
| 非法配置 | 对应组明确报配置错误 |
| 合法 Fired / 重复 Fired | 正确组新增 / 幂等，不污染另一组 |
| Resolved | 不清除名单 |
| 非法或过期事件 | 不更新；不可拿旧成功事件直接冒充新告警 |
| ETag 并发冲突 | 显式失败，不覆盖新值 |
| 钉钉非零 errcode | 运行失败；独立确认之前名单写入是否已成功 |

模拟事件只能证明控制器契约。完整闭环需要真实原生指标越阈值、真实 Fired、名单写入、通知成功，以及后续实际选路变化。触发器返回 HTTP 接收成功不够。

首次部署优先按 [部署步骤](deployment.md) 的第六步，在维护窗口临时降低阈值，以少量正常请求触发真实告警，不默认通过加压制造高延迟。阈值同时写入工作流校验和告警规则，必须暂停告警、排空运行后协调更新，不能只在 Portal 调低规则阈值。演练后恢复正式定义、阈值及名单，Resolved 不自动恢复名单。窗口与频率可通过 `window_size`、`evaluation_frequency` 配置，选项见部署文档；评估间隔不得大于窗口。仅调整这两个字段不改变工作流定义，但仍需重新生成告警并记录配置变更。

## 逐渐增加请求长度

以下是另外获授权的性能演练，不是部署闭环的必经步骤。从短的非敏感输入开始；确认 APIM 身份对所有模型部署都能推理，再测试约 64、512、2048、6000 tokens 的输入梯度。每档少量请求，观察实际 usage，而不是把字符数当 token 数。

输入越长不保证时延单调增加：缓存命中、后端负载、推理设置和输出长度都可能改变结果。聊天可以逐级提高输出目标，例如 128、512、1024 tokens；最大输出参数是上限，不是实际生成量保证。Embedding 可能先触发配额，或始终没有达到阈值。应记录“不越阈值”，不能把客户端耗时或手工构造事件当真实指标证据。

为每档记录输入/输出实际 token、原生 TTLT 时间桶、客户端耗时、状态和区域。预先设定请求数量、持续时间、费用和停止条件；持续 401/403、严重限流、影响业务或预算耗尽时停止增压。

测试准备与控制器动作分开记录。结束时清除临时后端、诊断头和模拟策略，按计划恢复名单/告警。不要无条件清空真实事故的降级标记。

## 手动恢复

1. 确认后端鉴权、模型健康、配额和容量，不能只因告警 Resolved 就认定可恢复。
2. 暂停对应告警或进入协调维护窗口，确认工作流没有在途写入。启用了 APIM 日志告警时，同一后端的 Foundry 与 p95 两条规则都要暂停。
3. 读取最新 Named Value 和 ETag，仅移除已恢复成员；列表空时填 `none`。
4. 使用精确 ETag 条件写入，发生冲突先重新读取并核对，不用通配覆盖。
5. 等待配置传播并观察真实请求，随后恢复原告警启用状态。

持续 Fired 的告警不保证每分钟重发。没有周期对账时，人工删掉降级项后也不保证立刻被再次加入。手动恢复必须同时审视当前指标与告警状态。

## 故障处理

| 症状 | 优先检查 |
|---|---|
| 控制器读取/写入 403 | 系统身份、两个新 Named Value 精确作用域 RBAC |
| 模型 401/403 | APIM UAMI、audience、Foundry 数据面授权和请求 ID；不是控制器 RBAC |
| 没有触发 | 指标是否可用、部署维度、阈值、规则是否启用、Action Group callback |
| p95 规则没有触发 | `GatewayLogs` 是否进入目标 workspace 的 `ApiManagementGatewayLogs`；BackendId/API/部署路径是否一致；窗口内正耗时且有后端响应的样本数是否达到 `min_samples`；日志延迟/采样及查询权限 |
| 日志 Resolved 但无健康样本 | 可能只是无数据或样本不足；不要据此清除降级名单，检查采集及真实请求 |
| 事件被拒绝 | 规则名称、资源/模型映射、指标契约、新鲜度 |
| ETag 冲突 | 管理员或其他运行是否更改同一名单 |
| 运行失败但名单已改变 | 查看通知阶段；更新不因通知失败而回滚 |
| 更新后暂时仍走旧成员 | 在途快照与网关传播；不能直接断言控制器没写入 |

失败写入不自动重试，不会定时修正。修复问题后基于当前事实执行新的有效操作。超出新鲜度的旧事件不得盲目重放；若需要手动处理，应留下独立审计记录。

## 更新和回滚

更改前保存现有 API policy、两个名单值、外部 backend ID、工作流定义、身份 principal ID 和告警状态。安全参数与 callback 只保存到受控秘密渠道，不提交 Git。

暂停告警、禁用工作流、排空运行后再变更。工作流更新保留系统身份；删除重建会生成新 principal ID，需要重新授权。修改路由、模型、阈值、规则名和 Named Value 名称时必须重新生成并协调部署所有关联对象。

回滚时恢复成套策略/名单/控制器定义，不混用“enabled”与“degraded”语义。先短请求验证，再恢复告警。停用本方案不需要删除外部 APIM、API、backend、UAMI、Foundry 或模型。

## 旧版可用名单迁移

如果旧名单表示“允许访问”，不能直接把值复制到 degraded 名单。按每组候选集合求补集：旧名单未包含的成员才转为降级。已有新名单时以新状态为准，不反复从旧名单覆盖。

确认所有 API、操作、片段和外部自动化都不再引用旧 Named Value 后，才可清理旧值和专用子资源 RBAC。旧部署、恢复与演练脚本也必须停用，否则可能重新写回旧语义。
